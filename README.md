# Kingline VPN

Исходный код сервиса Kingline: личный кабинет, административная панель,
Telegram-бот, интеграция Remnawave и автоматическое управление VPN-нодами.

## Структура

| Путь | Назначение |
|---|---|
| `staging/site/src` | React-интерфейс пользователя и администратора |
| `staging/site/backend` | Авторизация, подписки, поддержка, аналитика и защищённый API |
| `staging/bot` | Telegram-бот, платежи, подписки и служебные уведомления |
| `node_manager` | Установка и удаление нод, маршруты, квоты, РФ-выход и проверки |
| `smart_dns.py`, `sticky_dns.py` | Выбор входной ноды и закрепление сервера за подпиской |
| `subscription_gateway.py`, `subscription_modes.py` | Выдача подписок и TCP/RAW / XHTTP |
| `staging/ops` | Телеметрия, резервирование, диагностика и проверки доступа |
| `migration_tools` | Инструменты развёртывания и переноса |
| `staging/docs/service.md` | Основная документация архитектуры и эксплуатации |

История прежней версии бота сохранена в Git. В текущем дереве его код находится
в `staging/bot`; сайт и инфраструктура хранятся рядом в том же репозитории.
Файлы с датами, старые инструкции и одноразовые миграции описывают конкретные
прошлые состояния. Актуальное устройство системы описано в основной документации.

## Возможности

- Одна подписка для всех устройств, «Умный выбор» и ручные локации.
- VLESS TCP/RAW и XHTTP; явный выбор пользователя имеет приоритет.
- Установка ноды с SSH, проверка из РФ и подтверждение до публикации.
- Квоты трафика, веса, порядок ключей, маршруты между нодами и российский выход.
- CPU, RAM, диск, технические журналы и уведомления о доступности.
- Стоимость серверов, напоминания об оплате и ссылки на кабинеты провайдеров.
- Права администраторов, Telegram 2FA и CSRF для изменений.
- Отдельное хранение бизнес-данных и компактной технической телеметрии.

## Сборка интерфейса

Требуется совместимая с Vite 8 версия Node.js и pnpm.

```sh
cd staging/site
pnpm install --frozen-lockfile
pnpm build
```

Сборка создаёт `staging/site/dist`. Docker-образ сайта и бота использует эту
папку, поэтому интерфейс нужно собрать до `docker compose build`.

## Python и проверки

Python 3.12; зависимости сервиса и менеджера разделены:

- `staging/requirements.lock` — сайт и бот;
- `node_manager/requirements.lock` — служба нод.

Пример изолированного окружения для проверки менеджера:

```sh
python3.12 -m venv .venv
.venv/bin/pip install -r node_manager/requirements.lock pytest httpx
.venv/bin/python -m pytest node_manager/tests -q
```

Тесты используют временные хранилища и двойники внешних служб. Локальный макет
`staging/ops/ui_palette_preview.py` показывает интерфейс на вымышленных данных;
он не предназначен для публичного размещения.

## Конфигурация и развёртывание

Шаблон переменных — `staging/.env.example`. Настоящие `.env`, файлы токенов,
SSH-ключи, базы и инвентарь создаются и хранятся только на сервере. Пример не
заменяет полную конфигурацию установленного сервиса. Для запуска нужны настроенные
Remnawave, закрытые Unix-сокеты управляющих служб, DNS и сеть Docker.

В публичной копии адреса конкретной установки и персональные идентификаторы
заменены примерами. Они не являются рабочими адресами серверов. Публикация
исходников не переключает действующий сервис и не запускает рабочий бот.
На изолированной площадке платёжный шлюз остаётся тестовым; производственное
подключение требует отдельной настройки и проверки.

Порядок эксплуатации, роли серверов, права, проверки, резервирование и
восстановление описаны в [документации сервиса](staging/docs/service.md).
Сценарии `migration_tools` нужно выбирать по текущему состоянию установки:
это не универсальный установщик, который следует запускать целиком.

## Обновление публичной копии

`migration_tools/prepare_github_export.py` собирает исходники в отдельный свежий
Git-клон, сохраняя его историю. В выгрузку не входят пароли, токены, базы,
резервные конфигурации, журналы, скриншоты и установленные зависимости.
Необязательный `--redactions` принимает закрытую карту замены адресов установки
на примеры. Сам этот файл в репозиторий не включается.

```sh
python3 migration_tools/prepare_github_export.py --output /path/to/fresh-clone \
  --redactions /path/to/private-redactions.json
```

Перед отправкой проверяются состав коммита, отсутствие секретов, сборка и
профильные тесты. Скрипт подготовки не отправляет данные на GitHub сам.
