# Kingline — добавление серверов без фронтенда

На управляющем сервере `198.51.100.10` работает `kingline-node-manager.service`.
API слушает **только `127.0.0.1:8090`**. Команда `kingline-node` обращается к нему с отдельным административным токеном.

## Добавить Ubuntu-сервер

Поддерживаются чистые **Ubuntu 22.04, 24.04 и 26.04 LTS, amd64**, root по SSH, публичный IPv4, не менее 768 МиБ RAM и 3 ГиБ свободного места. Поверх чужих VPN, контейнеров и активного входного firewall установка не производится. Существующие Германия/Дания уже внесены в реестр; переустанавливать их этой командой не нужно.

Сначала войти на управляющий сервер с Mac:

```sh
ssh root@198.51.100.10
```

Затем выполнить, заменив `ВАШ_IP` и параметры тарифа:

```sh
kingline-node add \
  --ip ВАШ_IP \
  --name FI-Helsinki-01 \
  --display-name 'Финляндия · Хельсинки' \
  --flag-code FI \
  --country FI \
  --quota-tb 5 \
  --speed-mbps 1000 \
  --reset-day 19 \
  --password
```

Пароль будет запрошен скрытым вводом. Его нельзя передавать как аргумент командной строки. Для собственного ключа вместо `--password` использовать `--ssh-key /полный/путь/к/ключу`, для зашифрованного ключа добавить `--key-passphrase`. Путь относится к машине, на которой выполняется CLI. Если публичный ключ управляющего сервера уже установлен на новом сервере, параметры авторизации можно не указывать. Этот публичный ключ находится в `/opt/kingline-manager/data/id_ed25519.pub`.

Для нестандартного SSH-порта есть `--ssh-port`. Необязательный `--host-key-sha256 SHA256:...` сверяет известный отпечаток SSH-хоста до авторизации. Без него применяется TOFU: первый ключ запоминается, его последующая подмена отклоняется. При переустановке VPS ключ хоста нужно проверить и обновить в `known_hosts` вручную.

`--quota-tb` — десятичные ТБ, `--speed-mbps` — заявленная скорость в Мбит/с. 1 Гбит/с = 1000, половина гигабита = 500. Скорость используется как вес распределения, а не ограничитель канала. День сброса — 1–28; часовой пояс и точное совпадение с биллингом провайдера нужно учитывать отдельно.

Название и флаг передаются отдельно. В API это `display_name` (видимое название) и `flag_code` (две заглавные буквы, например `TR`, `DE`, `DK`). Backend сам собирает подпись, например `🇹🇷 Турция`. Если код флага не указан, используется `country`. `name` — необязательное внутреннее имя; по умолчанию строится из страны и IP. Старое поле `label` и параметр `--label` поддерживаются для совместимости. При одновременной передаче полного `label` и нового названия они должны совпадать.

CLI возвращает ID задания и ключ идемпотентности. Установка идёт в фоне:

```sh
kingline-node job ID_ЗАДАНИЯ
kingline-node jobs
kingline-node list
kingline-node standard
```

Повтор запроса с тем же `--idempotency-key` и теми же параметрами возвращает прежнее задание. Иной запрос на уже зарегистрированный IP отклоняется. После ошибки:

```sh
kingline-node retry ID_ЗАДАНИЯ
```

Если служебный SSH-ключ ещё не был установлен, повторить с `--password` или `--ssh-key`. Повторный запуск продолжает установку на том же IP и адресе управления. Ошибка сохраняет ноду вне автоматического выбора; установленные пакеты и WireGuard не удаляются, поскольку откат системного обновления небезопасен.

## Что делает установка

1. Проверяет SSH-хост, Ubuntu, архитектуру, ресурсы и отсутствие конфликтующих служб. Для автоматической установки также должны быть свободны TCP 80 и локальный TCP 8443.
2. Устанавливает отдельный ключ управления с ограничением источника адресом Литвы. Проверяет вход по нему и удаляет исходные реквизиты из задания. Пока задание ожидает первого входа, реквизиты хранятся зашифрованными; ключ шифрования доступен только root. После успешного запуска закрывает вход по SSH-паролю; вход по ключу управления остаётся. Для прямого входа с Mac нужен свой публичный ключ на новой ноде.
3. Обновляет пакеты Ubuntu, ставит Docker, WireGuard, nftables, Fail2Ban и синхронизацию времени. При необходимости автоматически перезагружает только новую, ещё не опубликованную ноду.
4. Выделяет адрес управления из `10.77.0.0/16`, добавляет peer на Литве без перезапуска остальных peers. API ноды 2222 доступен только из `10.77.0.1` через WireGuard.
5. Запускает закреплённый по SHA-256 контейнер Remnawave Node и привязывает **тот же существующий профиль**, что используют Германия и Дания. Включает учёт трафика, квоту и день сброса.
6. Применяет общий проверенный профиль TCP/RAW + REALITY Vision, SNI `www.samsung.com` и target `www.samsung.com:443`. Backend сверяет транспорт, fingerprint, SNI и закреплённый target; при расхождении установка останавливается. Экспериментальный модуль собственного HTTPS выключен после отката.
7. Проверяет реальный зашифрованный HTTPS, адрес выхода и UDP DNS. Проверка использует Xray 26.6.27 с текущим тестовым пользователем; его учётная запись должна оставаться активной.
8. Только после успеха публикует ручную локацию, добавляет ноду в общий «Умный выбор» и обновляет реестр. Контроллер DNS подхватит ноду примерно за 30 секунд; TTL ответа — 60 секунд.

Три существующие авторитетные DNS-реплики обслуживают и новые VPN-ноды. Разворачивать дополнительный публичный DNS на каждом новом сервере не нужно. Пользовательский трафик идёт непосредственно на выбранную ноду; Литва обслуживает управление и подписки.

## Удалить ноду — действие для будущей кнопки

```sh
kingline-node remove UUID_НОДЫ --name ВНУТРЕННЕЕ_ИМЯ --ip IP_НОДЫ
kingline-node removal UUID_НОДЫ
```

Фронтенд вызывает `DELETE /v1/nodes/{uuid}` с административным токеном и JSON `{"name":"TR-Turkey-02","ip":"198.51.100.33"}`. Имя и IP сверяются с выбранной записью. `GET /v1/nodes` возвращает `removable` и `removal_block_reason`: это готовые данные для состояния будущей кнопки. Последнюю действующую ноду удалить нельзя. Для Германии и Дании с разрешения владельца установлен служебный root SSH-ключ backend с ограничением источника `198.51.100.10`. Вход проверен, удаление доступно для всех трёх нод. Для старых Германии/Дании удаляется только роль VPN: их WireGuard и DNS сохраняются, поскольку это также авторитетные DNS-реплики.

Удаление последовательно исключает ноду из распределения, убирает её из общего и ручного профиля, останавливает VPN-контейнер, для автоматически добавленных нод отключает WireGuard и удаляет их peer/маршрут/разрешение из Литвы. Для старой экспериментальной конфигурации сохранён код удаления собственного HTTPS; на текущих нодах этот компонент уже удалён. Затем удаляются регистрации Remnawave, VPN-конфигурация и секрет на ноде, запись активного реестра и результаты проверок. ОС, SSH-доступ, базовый firewall и резервные копии сервера сохраняются. История установки и удаления остаётся для аудита. Кеши DNS могут сохранять прежний ответ до истечения TTL, но VPN-контейнер уже остановлен.

Статус доступен через `GET /v1/removals/{uuid}`: `running`, `failed` или `removed`, текущий этап и безопасный код ошибки. После частичного сбоя тот же DELETE продолжает очистку; успешное повторное удаление возвращает успех без обращения к серверу. Автоматически заново устанавливать ноду на уже выведенный IP пока нельзя: ответ `retired_address_requires_manual_reset` требует проверки/подготовки сервера и ручного освобождения адреса. Резервные архивы удаление не стирает.

## Единый VPN-профиль и пользователи

| Параметр | Значение |
|---|---|
| Протокол | VLESS |
| Транспорт | TCP/RAW (`tcp` для совместимости) |
| Защита | REALITY |
| Flow | `xtls-rprx-vision` |
| Порт | TCP 443 |
| Fingerprint | `firefox` |
| SNI / target | `www.samsung.com` / `www.samsung.com:443` |
| MUX / XHTTP | Не включены / отсутствует |
| Keepalive | idle 60 с, interval 30 с |
| Серверный TCP | BBR, MTU probing; `fq` как очередь по умолчанию |

Пользователи уже находятся в PostgreSQL Remnawave. Вторая независимая база пользователей не создавалась. Новые hosts используют общий inbound UUID; поэтому все пользователи с доступом к нему получают новую локацию при обновлении своей подписки. Это проверено с двумя отдельными временными пользователями. Общий inbound доступен текущей группе `Kingline Personal` и `Default-Squad` для будущих пользователей. Если позже создать отдельные группы с ограниченными правами, доступ нужно выдавать им намеренно.

Приложение должно обновить подписку, чтобы увидеть новую запись. Backend не может принудительно обновить закрытое приложение на телефоне. Общая запись «Умный выбор» остаётся одной; ручных записей становится по одной на ноду. Действующие соединения DNS между нодами не переносит.

## Умный выбор

Для каждого сервера каждые 30 секунд читается `trafficUsedBytes` из Remnawave:

```text
доступный остаток = max(0, 0.95 × месячная квота − учтённый трафик)
вес ≈ доступный остаток в ГБ × (скорость в Мбит/с / 1000)
```

Например, при нулевом расходе 5 ТБ / 1000 Мбит/с и 1 ТБ / 500 Мбит/с дают веса 10:1. Доля уменьшается по мере расхода; после 95% квоты вес равен нулю. Ручная локация при этом остаётся доступной. Отключённые, ещё не проверенные и выведенные на обслуживание ноды также исключаются. DNS-реплики дополнительно проверяют TCP 443 самостоятельно. Служба `kingline-tunnel-health.timer` примерно каждые три минуты проверяет реальный VPN, адрес выхода и UDP DNS. После двух последовательных неудач нода исключается из умного выбора; успех возвращает её. Результаты старше десяти минут, результаты другой конфигурации и результаты при недоступности обоих проверочных HTTPS-сервисов не влияют на DNS. Ручные профили сохраняются. В API `/v1/nodes` поля `routing.nodes[].vpn_probe_state` и `vpn_probe_excluded` отражают эту проверку.

У Германии и Дании скорость оставлена `null`, поскольку тарифная величина не подтверждена. Для них применяется одинаковый нейтральный множитель; у новой Турции указано 25 000 Мбит/с и 2 ТБ. Базовое соотношение весов при небольшом расходе составляет около 5:1:50. По последнему указанию владельца Германия и Дания участвуют в DNS-выборе (`maintenance=false`), Турция временно исключена (`maintenance=true`) из-за нестабильности. Все ручные профили доступны. После устранения проблемы Турцию можно вернуть командой `capacity UUID --maintenance off`. Заявленная скорость не проверялась нагрузочным тестом и не является гарантией пропускной способности. Указать фактическую скорость можно так:

```sh
kingline-node capacity UUID_НОДЫ --speed-mbps 1000
kingline-node capacity UUID_НОДЫ --quota-tb 5 --reset-day 19
kingline-node capacity UUID_НОДЫ --maintenance on
kingline-node capacity UUID_НОДЫ --maintenance off
```

Эти команды не обнуляют счётчик расхода. Remnawave считает VPN-трафик; его значение не равно гарантированно биллингу хостера с SSH, обновлениями и накладными расходами. Для этого оставлен резерв 5%. Распределяются DNS-ответы, а не гарантированные доли байтов или измеренный пинг каждого клиента.

## API для будущей панели и Raspberry Pi

Административный Bearer-токен хранится в `/opt/kingline-manager/data/admin.token`. Доступ сейчас возможен локально или через SSH-туннель; публиковать порт 8090 в интернет не нужно.

| Метод и путь | Назначение |
|---|---|
| `GET /v1/standard` | Стандарт без секретных ключей |
| `GET /v1/nodes` | Ноды, тарифы, расход и текущие веса |
| `POST /v1/nodes/preflight` | Проверка без установки |
| `POST /v1/nodes` | Задание установки; обязательный `Idempotency-Key` |
| `GET /v1/jobs`, `GET /v1/jobs/{id}` | Статус и этапы |
| `POST /v1/jobs/{id}/retry` | Продолжение после ошибки |
| `PATCH /v1/nodes/{uuid}` | Квота, скорость, день сброса, обслуживание |
| `DELETE /v1/nodes/{uuid}` | Удаление выбранной управляемой ноды; подтверждение имени и IP в JSON |
| `GET /v1/removals/{uuid}` | Статус и этап удаления, включая уже удалённые ноды |
| `GET /v1/openapi.json` | Схема API с административной авторизацией |
| `GET /v1/probes/targets` | Список нод для отдельного проверяющего модуля |
| `POST /v1/probes/reports` | Результаты проверки VPN, задержка, код ошибки |

Для Raspberry Pi предусмотрен **отдельный токен только для проверок**, не дающий административных прав. Его можно выпустить на управляющем сервере:

```sh
cd /opt/kingline-manager/app
/opt/kingline-manager/venv/bin/python -m node_manager.register_probe raspberry-home --region RU-home
```

Токен записывается в файл с правами 600. Модуль Raspberry Pi ещё не развёрнут: ему потребуются защищённое соединение с API и отдельный технический VPN-пользователь. Endpoint списка целей намеренно не выдаёт персональные ключи владельца.

При включённом для проверяющего модуля `--affect-routing` три последовательных неудачных проверки исключают ноду из общего DNS-выбора. Успех возвращает её. Повторные номера результатов отклоняются, время приёма задаёт сервер, результаты старше 5 минут перестают влиять на маршрутизацию. До развёртывания Raspberry Pi эта возможность не включена. Домашняя проверка РФ характеризует именно тот домашний провайдер, а не автоматически все мобильные сети страны.

## Проверки, хранение и восстановление

Код: `node_manager/`. Рабочая копия: `/opt/kingline-manager/app`. Изолированные зависимости: `/opt/kingline-manager/venv`, точные версии — `node_manager/requirements.lock`. SQLite заданий, реестр, SSH-ключ и токены: `/opt/kingline-manager/data`; доступ только root. Контроллер продолжает читать атомарно обновляемый `/opt/kingline-control/nodes.json`.

Пройдены 38 автоматических тестов: повторы запросов, сбои до и во время публикации, продолжение без дубликатов, шифрование реквизитов, защита API, отдельные права probe-токена, веса квота×скорость, устаревшие отчёты, название/флаг, совместимость старых запросов, удаление с частичным сбоем, повтор завершённого удаления, сохранение DNS старых нод и корректный приоритет SSH-настроек с восстановлением при ошибке, запрет публикации при неготовом HTTPS-target, целостность RealiTLScanner, удаление HTTPS вместе с нодой и исключение сломанного HTTPS из умного выбора. Отдельный тест на настоящем Remnawave подтвердил регистрацию и появление новой локации у двух пользователей без правок их аккаунтов; временные записи удалены. Через две действующие ноды проверены HTTPS и UDP. SSH-модуль успешно вошёл на Данию существующим ключом Mac и отказался переустанавливать работающую ноду. Итоговые отчёты: `verification-manager-live.json`, `verification-manager-panel.json`, `verification-vpn.json`.

Полная установка проверена 21 октября 2026 года на двух серверах. Прежний `198.51.100.36` (Ubuntu 24.04, `TR-Turkey-01`, 5 ТБ / 1000 Мбит/с) затем удалён через backend по просьбе владельца; статус `removed`. Повтор того же DELETE после развёртывания новой Турции возвращает успех и не обращается к серверу. VPN-контейнер, конфигурация, регистрации и peer прежней ноды удалены; архивы сохранены.

Новая Турция `198.51.100.33` (Ubuntu 26.04, `TR-Turkey-02`, 2 ТБ / 25 000 Мбит/с, сброс 19-го числа) установлена через тот же CLI с отдельными `display_name=Турция`, `flag_code=TR`. Задание `7e62d746-3d95-429c-86ba-981a015db0ac` завершилось `ready`. Проверены контейнер, WireGuard, firewall, Fail2Ban, HTTPS, UDP DNS и прямой выход с нового IP. Профиль появился у существующего пользователя без смены ключа; все четыре записи подписки прошли Xray-проверку. Все три DNS-реплики выдают новую Турцию. Существующие Германия и Дания не переустанавливались. Итоговая проверка реестра, API, удаления, SSH и DNS — `verification-manager-update.json`.

Образ Ubuntu нового хостера подключал парольные SSH-настройки перед стандартным каталогом настроек. Установщик теперь явно подключает собственный файл первым, проверяет `sshd -t` и действующие значения `sshd -T` (включая root), а при ошибке восстанавливает прежние файлы. Проверены новые входы с Mac и backend после отключения пароля. Порядок применения параметров соответствует [документации OpenSSH](https://man.openbsd.org/sshd_config).

Расширенный `backup-state.py core stage2` сохраняет исходники, настройки, токены и SSH-ключ backend, согласованный снимок SQLite и дамп PostgreSQL. Копии `de stage2`, `dk stage2` и `tr2 stage2` включают конфигурацию нод, разрешённые SSH-ключи и настройки SSH. Архивы четырёх действующих серверов сохранены на Mac и сверены по SHA-256; историческая копия прежней Турции также сохранена. Venv не архивируется: восстанавливается из lock-файла. Автоматическое расписание резервного копирования и ротация годового API-токена пока не настроены.

22 октября переход на собственный HTTPS-target откачен после сообщения владельца о неработающих ключах. Восстановлен прежний общий target; HTTPS-компоненты удалены с нод, таймер продления выключен. Backend с `enforce_uniform_profiles=true` проверяет порт, SNI, fingerprint и inbound всех hosts этого профиля; расхождение выдаёт `published_profile_drift`. Временный вариант AWS/36847 удалён. ## Участие в умном выборе

`smart_enabled` (boolean, по умолчанию `true`) задаётся в запросе добавления ноды и меняется через `PATCH /v1/nodes/{uuid}` вместе с параметрами ёмкости. В админке поле доступно при добавлении и в «Настроить». При `false` DNS-контроллер не использует сервер в автоматическом выборе, но его ручной профиль остаётся. Настройка не перезапускает VPN. Отсутствующее поле у старых нод трактуется как `true`; обслуживание и проверки доступности по-прежнему исключают ноду независимо от этого поля. Для веб-операций требуется право `nodes` и 2FA.

## Подключения и маршруты в разделе «Ноды»

Отдельный редактор «Настройки VPN» удалён по следующему запросу владельца. В «Нодах» доступны SNI/target для каждой ноды, порядок всех ключей подписки и графическое дерево подключения через другие ноды. Порядок требует `nodes`; SNI и маршруты — также `vpn_config` (по умолчанию выключено у делегированных администраторов). Общий профиль новых установок сохраняется.

Приватный API: `GET /v1/node-network`, `POST /v1/node-network/{connection,routes,order,rollback}`. Сайт использует `/api/admin/infrastructure/node-{network,connection,routes,order,job,rollback}` через прежний закрытый Unix socket. Подробности реализации, DNS-ограничений, учёта трафика, восстановлений и выполненных проверок: [NODE-NETWORK-REPORT.md](staging/NODE-NETWORK-REPORT.md).
