# Kingline: документация сервиса

Это основное описание нового сервиса: сайт, Telegram-бот, Remnawave, ноды, российский выход, оплата, данные и восстановление. Документ предназначен владельцу, администраторам с выданным правом и разработчику/ИИ, который продолжит работу.

Документ хранится в проекте `staging/docs/service.md`, попадает в Docker-образ и открывается в админке. «Скачать .md» и «Скопировать для ИИ» добавляют безопасный снимок текущих нод. Пароли, приватные ключи, пользовательские подписки и платёжные секреты в него не включаются.

## Статус проекта и границы

Новый сервис работает на `198.51.100.10`. Пользовательская площадка: https://test.edge.kingline.online. Имя содержит test, но дополнительного общего пароля и навязчивых тестовых надписей в кабинете нет. Это всё ещё изолированная площадка до отдельного разрешения владельца на переключение действующих пользователей.

Старый рабочий сервер `198.51.100.20` продолжает обслуживать людей через старый сайт, рабочего Telegram-бота и 3x-ui. Его не отключать, не удалять там 3x-ui, не менять боевые подписки и DNS ради проверки нового кода. Новый бот — отдельный https://t.me/stopRKNbot, с ограничением тестового доступа. Запуск двух экземпляров рабочего бота с одним токеном запрещён организационно: это ломает получение обновлений.

Данные пользователей, балансы, оплаты, привязки, поддержка и прежние идентификаторы подписок перенесены в новую базу. Старые токены подготовлены для совместимости на новом `/sub/...`; это не означает, что старые DNS/ссылки уже переключены для людей. Тестовые клиентские UUID отделены от действующих старых доступов.

На домашнем Raspberry прежний 3x-ui сохранён. Новая служебная нода Remnawave работает в отдельном контейнере. Удаление старого сервиса не входит в установку или замену российского выхода.

**Платежи на новой площадке сейчас имитируются.** `staging_server.py` заменяет платёжный шлюз на `TestPaymentGateway`. Реальные секреты рабочего платёжного провайдера не переносились. Успех тестовой оплаты не доказывает готовность реальной оплаты к производственному запуску.

## Архитектура и роли серверов

Пользователь получает одну подписку со списком профилей. «Умный выбор» — DNS-распределение прямого подключения, без центрального VPN-прокси. Отдельные страны остаются ручными профилями. Вводить особую подписку или ссылку для ПК в инструкциях владелец попросил не делать.

Путь обычного подключения:

```text
Приложение пользователя
  → выбранная зарубежная VPN-нода
  → интернет с IP этой локации
```

Для локации с цепочкой вход проходит через другую ноду. Передача между ними — TCP, REALITY-подключение пользователя заканчивается на конечной ноде. Счёт пользователя остаётся на конечной ноде. Главный сервис не передаёт этот VPN-трафик.

```text
Пользователь → входная нода → конечная нода → интернет
```

Если для конечной ноды включён российский выход, только перечисленные российские домены идут по отдельному частному каналу к российскому серверу:

```text
Зарубежная нода ┬→ обычный интернет, IP зарубежной локации
               └→ WireGuard → РФ-выход → российские сайты, IP РФ-выхода
```

Основные адреса на момент составления:

| Роль | Адрес | Назначение |
|---|---|---|
| Новый главный сервис | 198.51.100.10 | Панель, сайт, тестовый бот, очереди, DNS-контроллер |
| Германия | 198.51.100.31 | Пользовательская локация; RU-трафик сейчас напрямую |
| Дания | 198.51.100.32 | Пользовательская локация; RU через российский выход |

## Размещение на главном сервере

| Путь | Назначение |
|---|---|
| `/opt/remnawave` | Remnawave, PostgreSQL, Redis, страница подписок, subscription guard |
| `/opt/kingline-staging` | Новый сайт, бот, данные, журналы, образ и резервные копии |
| `/opt/kingline-manager/app` | Код root-службы управления нодами |
| `/opt/kingline-manager/venv` | Python-окружение службы нод |
| `/opt/kingline-manager/data` | SQLite менеджера, зашифрованные SSH-данные, служебный ключ и known_hosts |
| `/opt/kingline-control` | Инвентарь и управляющее состояние VPN/DNS/RU-выхода |
| `/run/kingline-site-admin/bridge.sock` | Частный административный Unix-сокет |
| `/run/kingline-subscriptions/gateway.sock` | Частный Unix-сокет выдачи подписок |

Основные loopback-порты: Remnawave API `3000`, native страница подписок `3010`, API менеджера `8090`, API сайта `8788`. Они не являются открытыми публичными интерфейсами управления. Публичный HTTPS обслуживается Caddy. Адрес панели: https://panel.kingline.online. Подписки публикуются через домен `connect.kingline.online`.

API сайта работает не от root, в read-only Docker-контейнере. Токен root-менеджера и приватный SSH-ключ не передаются в контейнер. Авторизованные команды идут к root-мосту через Unix-сокет; у Telegram-бота этого сокета нет. Для сокета важно `RuntimeDirectoryPreserve=yes`: пересоздание каталога под уже смонтированным Docker bind-mount приводило к недоступности моста.

## Личный кабинет и инструкции

Основные действия пользователя: оформить/продлить доступ, пополнить баланс, скопировать подписку, открыть инструкцию или поддержку. Выбор страны выполняется в VPN-приложении. Старый выбор локации в кабинете и раздел DNS пользователю не нужны и скрыты.

Инструкция разбита на три шага: установить приложение, добавить общую подписку, включить VPN. «Служба поддержки» доступна рядом с заголовком инструкции и в разделе неполадок. Запасной ссылки в пользовательском интерфейсе нет.

Каталог приложений один для сайта и бота. Основные приложения — v2RayTun и Happ; при недоступности v2RayTun в регионе предлагается Happ. Загрузки ведут к магазинам или официальному разработчику. Для компьютера могут показываться дополнительные клиенты. Нельзя обещать одинаковую поддержку всех механизмов учёта устройств любым клиентом.

Интерфейс покупки/продления показывает реальные этапы операции. Визуальная длительность позволяет прочитать результат, но не заменяет состояние backend. Повторный клик и перезагрузка страницы не должны создавать повторную оплату. Уважать `prefers-reduced-motion`; не прятать результат в исчезающей слишком быстро анимации.

Поддержка — отдельная переписка пользователя и администраторов с соответствующим правом. Вложения доступны только участнику переписки и администратору после авторизации. При изменении чата проверять минимум 320/390 px, переносы, высоту поля ввода, историю и область прокрутки; содержимое не должно наезжать друг на друга.

## Авторизация, 2FA и права администраторов

Сайт использует email, пароль, подтверждение почты и привязку Telegram. Не переносить бизнес-данные ценой сброса хешей паролей или потери связи аккаунтов. Конкретные SMTP-настройки относятся к окружению; не считать реальную рассылку готовой только по доступности формы.

Вход начинается в тёмной теме. На экране Telegram 2FA убран лишний верхний блок Kingline. Это оформление; серверная проверка 2FA обязательна независимо от видимости блоков.

Владелец имеет полный доступ и управляет администраторами. У делегированных администраторов права хранятся отдельными полями `web_admins.can_*`. Новые инфраструктурные права по умолчанию выключены. Для любого защищённого раздела нужны вход, статус администратора, требуемое право и подтверждённая административная 2FA. Изменения дополнительно проходят CSRF/Origin-защиту.

| Право | Возможности |
|---|---|
| `analytics` | Аналитика и соответствующие сведения активности |
| `balance`, `message`, `block`, `delete_users` | Соответствующие действия с пользователями |
| `support` | Административная поддержка |
| `payments`, `promos`, `broadcast` | Платежи, промокоды, общие сообщения и объявления |
| `nodes` | Ноды, установки/удаления, квоты, флаги и замена РФ-выхода |
| `vpn_config` вместе с `nodes` | SNI/target и маршруты между нодами |
| `node_credentials` вместе с `nodes` | Отдельное раскрытие сохранённых SSH-данных |
| `technical` | Технические логи и состояние служб |
| `documentation` | Документация и её выгрузка для ИИ |

Скрытая вкладка не является защитой. Проверка права выполняется на сервере, в том числе для скачивания документации. Пользователь без права не должен получить содержимое прямым запросом к API. Документация раскрывает архитектуру, поэтому публиковать её в открытых assets нельзя.

## Сообщения и объявление в VPN-приложении

Раздел «Отправить всем» переименован в **«Сообщения»**. Отдельная форма сохраняет общее текстовое объявление над профилями в v2rayTun; прежняя рассылка Telegram/email остаётся самостоятельной формой и сохранение объявления её не запускает. Доступ к чтению/изменению требует прежнего права `broadcast` и административной Telegram 2FA. POST `/api/admin/messages/announcement` дополнительно проверяет CSRF/Origin. GET возвращает текущий текст, время и ревизию; сохранение устаревшей ревизии отклоняется с `announcement_changed` (409), чтобы администраторы не затёрли изменения друг друга.

Одна строка `subscription_announcement(singleton=1,text,updated_at,revision)` находится в бизнес-SQLite. Текст ограничен 500 символами, переводы строк поддержаны, управляющие знаки запрещены. «Убрать объявление» сохраняет пустой текст. В журнале действий — `subscription_announcement_change` с длиной, признаком включения и ревизией, без содержимого. Никакие пользовательские UUID, сроки, ключи, маршруты, HWID и RAW/XHTTP при этом не меняются.

Частный `subscription_gateway.py` читает эту строку read-only через уже настроенный `transport-policy.json.business_db` и добавляет `announce: base64:<UTF-8>` только к успешным ответам подписки (включая HEAD), исключая HTML и отказы HWID. Новая строка заменяет native `announce` и убирает прежний `announce-url`: текст не получает чужую кликабельную ссылку. До первого сохранения native заголовки сохраняются. Пустой управляемый текст полностью удаляет оба заголовка `announce` и `announce-url`, включая native значения: `base64:` без содержимого не отправляется, поскольку такой непустой маркер может оставлять пустое место в клиенте. В предпросмотре пустой текст также не создаёт абзаца/разделителя. Изменение приходит при следующем успешном обновлении подписки; поведение кэша конкретной версии приложения нужно подтвердить на устройстве. Ошибка чтения необязательного объявления логируется только с классом ошибки и **не ломает выдачу VPN-конфигов**. Совместимый `/sub/...` сайта также пропускает `announce`/`announce-url`. Новых публичных/привилегированных мостов не добавлено.

Пользователь увидит изменение при следующем обновлении своей прежней подписки, без переустановки. Это не мгновенное push-уведомление. Другие клиенты могут не показывать объявления. Формат подтверждён [официальной документацией v2rayTun](https://docs.v2raytun.com/overview/supported-headers); предпросмотр в админке приблизительный, окончательный вид и очистку сохранённого текста нужно проверять в фактической версии приложения. При выпуске не публиковать пробный текст всем и не использовать рассылку для проверки.

## Пользователи, Remnawave и подписки

Сайт и бот используют Remnawave API v3 через адаптер, а не обращаются к старым 3x-ui. Для установленной версии панели основной идентификатор пользователя числовой. Таблица `remna_links` сопоставляет старый `sub_id` и профиль новой панели. Метки и группы отделяют перенесённые тестовые записи от служебных пользователей.

При выдаче/продлении сохраняются идентичность подписки и точный срок. Не создавать новый UUID при каждом продлении. Не включать все перенесённые старые записи автоматически: истёкшие/заблокированные доступы должны остаться такими. Запись прошлой даты в панели может требовать выключения профиля вместо некорректного PATCH; исходная бизнес-дата сохраняется в базе.

Путь совместимости `/sub/<старый токен>` на новом сайте проверяет блокировку и срок в бизнес-базе и панели, затем выдаёт новую подписку. Токен в URL — секрет доступа; его не писать в access-log, документацию или снимок ошибки.

Название группы подписки в приложении — **«Kingline VPN · Имя»**: имя из связанного аккаунта сайта (`web_accounts.name`), при его отсутствии — сохранённое имя Telegram (`users.tg_name`). `subscription_modes.profile_title` читает только владельца конкретного `remna_links.short_uuid` или существующего служебного сопоставления `transport-policy.json.aliases`; отрицательный web ID уже объединённого аккаунта не раскрывает имя новой связанной учётной записи. Текст однострочный, до 80 символов имени, без управляющих/двунаправленных знаков; email и технические заглушки не используются как имя. Если имя отсутствует, остаётся «Kingline VPN». Неизвестные/служебные подписки без бизнес-сопоставления сохраняют native заголовок. Ошибка чтения имени не мешает выдаче ключей и логируется только с классом ошибки.

`profile-title: base64:<UTF-8>` устанавливается частным шлюзом только после успешного ответа панели, исключая HTML и отказы HWID, также для HEAD. Совместимый сайт передаёт его без прежней замены на общее название. UUID, URL подписки, названия локаций и настройки VPN не меняются; имя обновляется при обычном обновлении подписки в приложении. Новых полей, баз или привилегий нет. Некоторые клиенты могут сохранять вручную заданное локальное название.

В подписке сейчас «Умный выбор» и ручные локации. Порядок меняется в «Ноды → Порядок ключей» и появляется в приложении после обновления подписки. Само приложение может включить собственную сортировку. Добавление ноды создаёт общий host профиля — не требуется переписывать каждого пользователя вручную.

Служебные пользователи `SERVICE_PROBE` и `RU_ROUTER` не являются клиентами. Первый проверяет туннели; второй авторизует внутренний российский выход. Не включать их трафик в пользовательский онлайн и не выдавать их ссылки людям.

## Три устройства и совместимость клиентов

В Remnawave включён HWID и лимит три зарегистрированных устройства на подписку целиком, а не по три для каждой страны. Новое создание и продление сохраняют лимит. Прокси передаёт `x-hwid`, `x-device-os`, `x-ver-os`, `x-device-model` и диагностические заголовки отказа.

Это ограничение выдачи конфигурации поддерживающим клиентам. Один публичный IP не равен одному устройству: за NAT может быть несколько устройств, а телефон меняет адрес. Копирование готового VLESS-ключа и подделку клиентского идентификатора такой лимит полностью не предотвращает.

При строгом лимите обычный запрос без HWID может вернуть пустую конфигурацию. Совместимость зависит от клиента и его версии; её нужно проверять фактическим запросом приложения, а не только подстановкой его User-Agent. Владелец отклонил особые PC-ссылки в инструкции: не возвращать их. Серверный эксперимент с явным параметром идентификатора не является отдельной пользовательской подпиской и не должен предлагаться как новая обязательная ссылка. Решение совместимости обычного адреса с такими клиентами требует отдельного согласования ограничений; не отключать глобально HWID молча.

Ошибка REALITY `received real certificate` означает, что клиент получил обычный сертификат вместо ожидаемого REALITY-ответа. Причины могут включать неверные/устаревшие параметры, несовместимое ядро, время устройства или сетевую переадресацию. Проверка сервера из Литвы не доказывает исправление на рабочем ПК или у конкретного российского оператора. Не отключать проверку сертификатов ради исчезновения сообщения.

## Надёжная оплата и выдача доступа

Бизнес-операция получает устойчивый ключ повтора. Намерение создать доступ, точный срок и списание баланса сохраняются транзакционно до внешнего обращения. Повтор использует сохранённый план и не пересчитывает срок от нового времени.

`subscription_operations` хранит намерение, `request_key`, план, состояние, число попыток, срок повтора и результат. Для пользователя допускается одна незавершённая выдача. Состояния внутреннего процесса включают `provisioning`, `retrying`, `ready`; сайт дополнительно хранит пользовательские задачи в `web_account_jobs`.

Если панель приняла запрос, но ответ потерялся, повтор не должен создать второй доступ или второе списание. Сверяются сохранённые идентификаторы и точное окончание. После успеха результат, бизнес-поля и состояние задачи фиксируются одной транзакцией. Повторы используют общий межпроцессный lock, чтобы сайт и бот не выполняли одну выдачу одновременно.

Интервалы повторов увеличиваются с ограничением до часа. Worker сайта и механизм бота восстанавливают незавершённые операции после перезапуска. Пользователь видит создание/ожидание/готовность, а не ложный успех по факту нажатия кнопки.

Платёжное подтверждение и предоставление VPN — разные этапы. При неполадке панели не просить пользователя платить повторно. Перед настоящим запуском проверить подпись webhook, идемпотентность платежа, повторные уведомления провайдера, сверку суммы/валюты и выдачу после тайм-аута. Существующий preview использует имитацию, а не эти боевые секреты.

## Транспорт VPN

Рабочий публичный стандарт: VLESS, RAW/TCP, порт 443, REALITY, `xtls-rprx-vision`, клиентский fingerprint Firefox. Входящие настройки унифицированы. Историческое имя тега `KINGLINE_XHTTP_REALITY` не означает, что транспорт сейчас XHTTP.

С 23 октября 2026 общий SNI — `edge.kingline.online`, target — `127.0.0.1:8443` на самой ноде. Nginx в отдельном ограниченном контейнере `kingline-cover` обслуживает обычный HTTPS с действительным сертификатом TLS 1.3/h2. Target намеренно локальный: указывать собственный публичный `:443` нельзя — это петля в тот же REALITY-вход. При обычном TLS-запросе без VPN-аутентификации отвечает наш HTTPS, а не чужой популярный сайт. Порт 8443 слушает только loopback; Remnawave API 2222 остаётся в служебной сети. Контейнер read-only, лимит 96 МиБ, журналы ограничены. Не добавлены характерное throttling fallback, случайные отпечатки, MUX или экспериментальные маски.

Выдаваемые ручные профили используют постоянные имена `n-<UUID без дефисов>.edge.kingline.online`; `node_domains=true` включает этот контракт. При прямом входе A-запись указывает на IP самой ноды. При уже настроенной владельцем цепочке имя конечной локации указывает на входной сервер, а порт остаётся назначенным цепочке. Нового посредника миграция не добавляет. «Умный выбор» сохраняет персональное имя и суточное закрепление, общий SNI/REALITY-ключ совместимы на всех участвующих нодах.

`node_manager/domains.py` сверяет A-записи на всех трёх авторитетных DNS перед публикацией. Отказ DNS запрещает публикацию новой ноды: отката к выдаче голого IP нет. Имя сохраняется при перестройке маршрута; смена DNS входит в восстановление сетевой операции. Удаление ноды удаляет только принадлежащую менеджеру запись с точным шаблоном, не затрагивая сайт, Auto и остальные данные зоны. Скрытие сохраняет DNS, но убирает профиль/участие через существующую процедуру. Фактические IP продолжают храниться в закрытом инвентаре и использоваться независимыми проверками.

Сертификат для `edge.kingline.online` и `*.edge.kingline.online` выпускается DNS-01 через наши PowerDNS без открытого ACME API. Закрытый ключ хранится только на управляющем сервере и нодах. Новая нода получает HTTPS до запуска рабочего REALITY и публикации. Таймер `kingline-cover-maintenance.timer` дважды в сутки проверяет продление, доставку сертификата и сверяет доменные записи; неудавшаяся доставка повторяется. Политика `cover-policy.json` добавляет проверку публичного HTTPS в контроллер. Служебный порт для проверки кандидата 1443 и временные контейнеры после проверки удаляются.

Предыдущий опыт с собственным HTTPS 22 октября откатывался после отказа на телефоне, причина не установлена. Новое включение предварительно проверено отдельно: Firefox/Chrome и сохранённый старый SNI, HTTPS/UDP-DNS из Литвы, передача известного 1 МиБ из домашней сети РФ. Затем повторены проверки на настоящем 443; это не проверка iOS TUN и не доказательство доступности у Билайна. Старое имя временно остаётся допустимым на сервере для закэшированных рабочих ключей, но новые подписки выдают только собственный SNI. UUID, REALITY-ключи, short ID, устройства, лимиты и пользовательские ссылки не менялись. Не публиковать privateKey из config-profiles.

Домен не скрывает IP: DNS и сертификаты публичны, один собственный SNI может быть заблокирован вместе со всеми нодами. Совпадение домена/сертификата/адресов убирает конкретное несоответствие, но не доказывает снижение вероятности блокировки и не скрывает форму трафика от любого DPI. Официальные требования и ограничения: [REALITY](https://xtls.github.io/en/config/transports/reality.html), [пример XTLS Vision](https://github.com/XTLS/Xray-examples/blob/main/VLESS-TCP-XTLS-Vision-REALITY/REALITY.ENG.md).

Разный SNI у ноды может сделать её несовместимой с общим DNS-профилем. Backend исключает такую локацию из «Умного выбора», оставляя ручной ключ. Схема не обещает обход любого IP-блокирования или разрешительного списка оператора. Нужна проверка с реальной сети РФ.

Публичные параметры, UUID пользователей и ручные маршруты не должны меняться при переключении внутреннего российского выхода. Для внешних клиентов не требуется ещё один профиль РФ.

## Выбор TCP/RAW и XHTTP пользователем

В боте кнопка кабинета называется «Мой кабинет». В веб-кабинете сразу под продлением находится «Способ подключения», а в боте выбор доступен из «Ключ → TCP/RAW или XHTTP».

Оба варианта — VLESS. TCP/RAW + REALITY + Vision остаётся по умолчанию и рекомендуется для iOS с учётом прежних обрывов XHTTP на iPhone. XHTTP предлагается для Android в клиентах с ядром Xray (v2rayTun/Happ/v2rayN): он передаёт трафик через HTTPS, но не имеет гарантированного превосходства в защите или обходе DPI. Память iOS TUN этим выпуском не измерена. При обрывах можно вернуться на RAW.

Выбор общий для учётной записи и всех её устройств. Одна прежняя ссылка подписки сохраняется. После переключения пользователь обновляет подписку в приложении. Действующие RAW-ключи не отзываются, стоимость, срок, баланс, UUID, суточное закрепление IP и лимит трёх HWID не меняются.

Общий `staging/bot/vpn_preferences.py` хранит строку `vpn_preferences(tg_id, transport, updated_at)` в бизнес-SQLite. POST `/api/account/vpn-mode` требует текущую сессию, JSON, проверку Origin и CSRF-заголовок; принимает только `raw`/`xhttp`, без произвольного ID пользователя. Бот использует ID автора callback. Заблокированный или неизвестный пользователь не может менять режим. `KINGLINE_XHTTP_READY=1` открывает выбор после проверок; RAW доступен независимо от него. Продления не стирают предпочтение. При привязке Telegram переносится последний явный выбор объединяемых аккаунтов. Раздел не создаёт VPN-учётных записей и не выполняет оплат.

### Определение ОС и ночной выбор режима

С 24 октября после успешной авторизации/восстановления сессии на сайте и после проверки Telegram initData в Mini App сервер записывает тип ОС. Источники: User-Agent, стандартный `Sec-CH-UA-Platform`, невидимые заголовки `X-Kingline-Platform`/`X-Kingline-Client` от кабинета. Последние передают `Telegram.WebApp.platform` в Mini App и признак iPad в режиме настольного Safari. Новых элементов в клиентском кабинете нет. Значения сообщает клиент: это сведения об ОС при входе, не доказательство физического устройства, не HWID и не средство авторизации. Гостевые запросы и невалидный Telegram initData не привязывают наблюдение к аккаунту. См. [Telegram Mini Apps](https://core.telegram.org/bots/webapps#initializing-mini-apps) и [Client Hint Platform](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-CH-UA-Platform).

Таблица `account_platforms` содержит максимум шесть строк на аккаунт (iOS/iPadOS, Android, Windows, macOS, Linux, неизвестно): первое/последнее обнаружение и признаки входа через сайт/Mini App. Новые записи не содержат полных UA, IP, cookies, Telegram initData или отпечатков. Повторные входы обновляют время не чаще раза в пять минут; история каждого посещения не создаётся. Сведения остаются до удаления аккаунта; автоматический выбор учитывает все обнаруженные мобильные ОС. Администратор с правом «Аналитика» видит ОС, источник/дату входа и статус выбора в существующей карточке устройств. Сетевые предположения показываются лишь при отсутствии наблюдений входа.

Новый аккаунт всегда начинает с VLESS TCP/RAW. По уточнению владельца автоматическое решение разрешено **только один раз за жизнь аккаунта**. Первое подтверждённое при входе мобильное устройство ставит решение в очередь на ближайшие **03:30 МСК**: Android без обнаруженного iOS выбирает XHTTP, iPhone/iPad или обе мобильные ОС — RAW. Даже сохранение исходного RAW считается выполненным автоматическим решением. После него новые входы и новые устройства продолжают записываться, но больше не меняют транспорт и не создают очередь. Если после уже выбранного XHTTP появился iPhone, автоматического возврата нет: режим меняется вручную пользователем или уполномоченным администратором. Десктопные/неизвестные ОС не расходуют этот единственный выбор. Учитываются только `account_platforms` с признаком входа через сайт/Mini App; предположения по посещённым доменам, сетевым запросам и VPN-логам не используются. Повторные входы не сдвигают уже назначенную очередь. Приложение получит новый конфиг при следующем обычном обновлении единственной прежней подписки; действующий туннель принудительно не разрывается, уведомления не рассылаются.

У `vpn_preferences` используются `selection_source` (`default`/`auto`/`manual`), `manual_selected_at`, `auto_due_at` и `auto_completed_at`. Последнее поле — постоянный маркер выполненного единственного автоматического решения. Уже существующие строки с `selection_source='auto'` при миграции получают этот маркер без смены транспорта, их старая очередь снимается. **Любое успешное ручное сохранение, даже текущего значения, навсегда запрещает автоматическую смену** на аккаунте. Старые строки до первой миграции признаются ручными: тот код создавал их только по явному действию пользователя. Отсутствие строки означает RAW по умолчанию. При объединении сайта/Telegram ручной выбор любой стороны важнее автоматического, выполненное автоматическое решение важнее нового значения по умолчанию; между двумя ручными сохраняется последний. Маркер выполнения объединяется с обеих сторон и не обнуляется, поэтому привязка Telegram не даёт второго автоматического выбора. Удаление аккаунта очищает и эти метаданные.

Существующий worker сайта раз в минуту вызывает `apply_due`, обрабатывая до 100 записей за проход. Исполнение допускается только с **03:30 до 05:00 МСК**; пропущенное из-за простоя задание ждёт следующую ночь. При выключенном `KINGLINE_XHTTP_READY` переходы не выполняются. Проверка заблокированного пользователя, отсутствия ручного выбора и `auto_completed_at`, вычисление приоритета ОС и запись маркера выполнения идут в одной `BEGIN IMMEDIATE` транзакции. Одновременный ручной выбор всегда остаётся последним решением; повторный проход идемпотентен. В диагностике — `vpn_auto_transport_applied` со счётчиками `completed` (включая исходный RAW) и `changed`, `vpn_auto_transport_failed`/`account_platform_record_failed` с классом ошибки, без персональных идентификаторов.

### Протокол конкретного пользователя и истёкший доступ

В «Пользователи → Открыть пользователя» вместо архивного переключателя локаций — TCP/RAW и XHTTP. POST `/api/admin/user/vpn-mode` принимает `tgId` существующей бизнес-записи и `transport`. Обязательны текущая административная сессия, Telegram 2FA, CSRF/Origin и отдельное право **`user_transport` («Протоколы пользователей»)**. У обычных/существующих администраторов оно по умолчанию выключено, владелец может выдать его в разделе «Админы». Операция сохраняет ручной выбор и снимает очередь автоматики, включая уже выбранное значение. Можно подготовить транспорт заблокированной записи, но блокировка/срок/баланс/UUID/ссылка не меняются и новый VPN-доступ не создаётся. В журнал действий записывается `user_transport_change`. Bootstrap возвращает текущий транспорт и признаки ручного/завершённого автоматического выбора; после сохранения карточка обновляется. Отдельные локации пользователь выбирает в VPN-приложении.

При истёкшем доступе кнопка копирования и предпросмотр ссылки скрыты. В карточке — красная кнопка «Продлить за … ₽», приглушённая строка «Ваша ссылка сохранена» и пояснение о сохранении прежней подписки. После успешного продления копирование возвращается. Изменения только визуальные, доступ по-прежнему проверяется сервером и Remnawave. Интерфейс дополнительно учитывает `expiresAt` таймером и при возврате во вкладку: старое `active=true` в открытом кабинете не оставляет кнопку подключения после окончания срока. Валидный новый срок после продления возвращает активное состояние. Заблокированным пользователям показывается поддержка; новым аккаунтам без ссылки — прежнее предложение пробного доступа.

Миграция выполняется при старте сайта, под savepoint, и совместима с текущим шлюзом подписок (он читает только `transport`). При откате к старой трёхколоночной версии модуля нельзя просто вернуть старый контейнер: её `INSERT VALUES` несовместим с расширенной таблицей. Нужен адаптированный старый writer с явным списком колонок либо обратная миграция только `vpn_preferences` с сохранением актуальных трёх полей. Не восстанавливать всю бизнес-БД поверх новых оплат ради отката этого изменения. Резервные копии остаются только на сервере.

У рабочего профиля появляется второй VLESS inbound `KINGLINE_XHTTP_TLS`, только `127.0.0.1:10080`, без Vision. Публичный порт остаётся 443: обычный TLS через fallback REALITY попадает в собственный Nginx, который маршрутизирует выделенный путь в локальный XHTTP через h2c `grpc_pass`. Сертификат проверяется клиентом; `allowInsecure` не используется. Удалённой прослойки/CDN нет. Российская маршрутизация и имеющаяся цепочка Турции продолжают действовать через общие серверные правила. Служебный API остаётся закрытым. При текущем fallback `xver=0` исходный IP клиента не передаётся в локальный XHTTP: входные журналы могут показывать loopback. Учёт UUID/трафика и лимит HWID не зависят от этого адреса; определять число физических устройств по нему нельзя. Нативные HTTP-запросы подписки продолжают передавать реальный IP.

Менеджер включает оба inbound у новой ноды; HTTPS-путь готовится до публикации, затем проверяются RAW и XHTTP с HTTPS и UDP-DNS. Сбой любого из двух не публикует новую ноду. Обслуживание сертификатов учитывает путь в версии, чтобы не удалить его при продлении. Клонирование профиля сохраняет дополнительный inbound и его права в squad. Ручной профиль с чужим SNI не преобразуется: наш сертификат не может подтвердить чужой домен.

Корневой адаптер читает предпочтение из бизнес-БД только на сервере, сопоставляя native shortUuid с `remna_links/users`. Исходный технический профиль владельца связан через закрытый alias в `transport-policy.json`; чужой пользователь не выбирается ID из запроса. XHTTP добавляет доверенный внутренний заголовок, а SRR панели выбирает Base64 без отключения HWID. Одноимённый входящий заголовок клиента отбрасывается. `subscription_modes.py` меняет только транспорт/TLS-параметры выданных VLESS URI, сохраняя порядок, адреса, порты, пользователя и Auto. Неожиданный формат или ошибка чтения предпочтения возвращает отказ, а не другой режим. RAW-ответы не преобразуются. Для XHTTP использовать общую ссылку в Xray-клиенте, а не дополнительные native пути чужих форматов.

Исправление 24 октября: `mode=ro` у SQLite не отменяет необходимость создать служебные `-wal`/`-shm`, когда последнее подключение закрылось и SQLite их удалил. `ProtectSystem=strict` у `kingline-subscriptions` раньше запрещал это, вызывая `OperationalError` и HTTP 503 даже для зарегистрированного телефона. Проверка из обычной root-сессии могла временно замаскировать сбой, создавая эти файлы. Unit разрешает служебные записи в `/opt/kingline-staging/data`; само подключение остаётся `mode=ro` и выполняет только SELECT. Не применять `immutable=1` к изменяемой бизнес-БД и не удалять WAL вручную. Поведение подтверждено [документацией SQLite](https://sqlite.org/wal.html#read_only_databases).

Нативные отказы HWID не преобразуются в XHTTP: заголовки `x-hwid-not-supported`, `x-hwid-max-devices-reached` и `x-hwid-limit` передаются вместе с исходным статусом/телом, включая используемый установленной версией HTTP 200 с пустым телом. Ранее такой ответ ошибочно превращался в 503. Лимит устройств не отключается; HEAD также не конвертируется. См. [HWID Remnawave](https://docs.rw/features/hwid-device-limit/). Журнал `kingline-subscriptions` содержит безопасные `subscription_failure` с причинами `mode_lookup`, `upstream_unavailable`, `conversion`; без URL, shortUuid, HWID, ключей, IP и текста исключений. Успешные запросы не протоколируются.

XHTTP `mode=auto`, ALPN h2, без экспериментальных extra/XMUX-переопределений; при TLS h2 клиент выбирает stream-up. Основная часовая проверка РФ остаётся проверкой RAW; отдельные реальные XHTTP-проверки выполнены при выпуске и требуются при установке ноды. Домашняя проверка не подтверждает доступность у другого провайдера. Источники: [XHTTP — описание разработчика](https://github.com/XTLS/Xray-core/discussions/4113), [Remnawave Response Rules](https://docs.rw/learn-en/routing-rules/).

## Умный выбор: закрепление, веса, отказ

Для каждой активной подписки генерируется непрозрачное имя `u-<HMAC>.auto.edge.kingline.online`. Оно не содержит токен подписки и числовой ID открытым текстом. Соответствие хранится только на главном сервере. Три DNS-реплики получают одинаковое предпочтение для подписки.

Выбор сохраняется в SQLite минимум на 86400 секунд. Обычные изменения оставшегося трафика не двигают пользователя внутри суток. После срока выполняется пересмотр; сервер остаётся прежним, если остаётся победителем. Это не принудительная суточная ротация.

Взвешенный rendezvous hashing распределяет разные подписки независимо. Чем больше остаток квоты и заявленная скорость, тем больше вес новых назначений. Не пытаться балансировать каждый DNS-запрос случайно: это меняет IP слишком часто и мешает пользовательским сессиям.

```text
доступный остаток = max(0, 0.95 × месячная квота − учтённый расход)
коэффициент скорости = Мбит/с / 1000
вес ~ остаток в ГБ × коэффициент скорости
```

При неизвестной старой скорости используется нейтральный коэффициент 1000 Мбит/с; это не измеренная пропускная способность. ТБ задаются десятичными единицами `10^12` байт. Дата сброса задаётся отдельно каждому серверу; 29–31 в коротком месяце означает последний день. Контроллер учитывает текущий расход, а для транзитных нод — доступные физические счётчики, чтобы не игнорировать дополнительный трафик цепочек.

Раннее переназначение допускается при сбое, обслуживании, выключении участия, несовместимом SNI/цепочке или исчерпании доступной квоты. Native PowerDNS дополнительно проверяет TCP-порт. DNS-кэш клиента и уже открытые соединения могут сохранять старый путь; TTL не гарантирует мгновенное переключение любого приложения.

Состав Auto задаётся живым инвентарём. Германия скрыта по решению владельца после отказа TCP из РФ; Дания, Литва и Нидерланды доступны. Турция отключена от Auto из-за нестабильности и цепочки. Участие меняется отдельно от российского выхода. Галочка RU не делает ноду участником Auto и не убирает её из него.

Основные файлы: `nodes.json`, `smart-dns-status.json`, `sticky-dns.sqlite3`, `sticky-dns.key`, `sticky-subscriptions.json`, `sticky-policy.json` в `/opt/kingline-control`. Секретные файлы не скачивать на Mac и не отдавать браузеру. Закрытый адаптер подписки меняет только адрес Auto, сохраняя ручные профили и криптографические параметры.

## Добавление зарубежной ноды

В админке «Ноды → Добавить ноду» вводятся публичный IPv4, имя/страна/флаг, трафик в ТБ, скорость в Мбит/с, дата ежемесячного сброса и SSH-вход root. Можно добавить заметку, стоимость и отдельный **«Сайт провайдера»** — сайт покупки или кабинет хостинга. Ссылка открывается в новой вкладке из карточки ноды и формы настройки. Её можно изменить или очистить в «Настроить». Пароль нужен для первого входа; в процессе устанавливается служебный SSH-ключ backend.

`provider_url` хранится в закрытом `site-admin.sqlite3.inventory.metadata`, отдельно от заметки и зашифрованного SSH-секрета. Изменяется через существующие `/add` и `/update` с правом `nodes`, Telegram 2FA и CSRF. Допускаются только HTTP/HTTPS без логина/пароля в URL; адрес без схемы дополняется HTTPS. Backend не загружает содержимое сайта по этой ссылке. Старые записи возвращают пустое поле; запрос старого клиента без `provider_url` сохраняет прежнюю ссылку, явная пустая строка удаляет её. Сохранение не меняет VPN, квоты или напоминания. Место покупки существующих нод подтверждено письмами активации и/или инвентарём: Германия — Layer7, Дания — Webdock, Турция — ServerQ, Нидерланды — quicksrv, литовская нода — Hostinger. Владелец сети из WHOIS сам по себе не считается доказательством продавца.

По умолчанию включены две независимые настройки: «Участвует в Умном выборе» и «Российские сайты через РФ-выход». Обе можно снять сразу или изменить позже. Для Германии RU сейчас выключен по решению владельца.

Обычный установщик рассчитан на свежую поддерживаемую Ubuntu amd64. Он проверяет системные требования и занятые службы, устанавливает зависимости/контейнер, служебную сеть, связывает Remnawave, проверяет реальный HTTPS и UDP-DNS из Литвы. Затем обязательны проверка из домашней сети РФ и решение администратора; автоматической публикации после установки больше нет. Не удалять найденный чужой VPN молча: используется отказ preflight и отдельная миграция.

После подготовки задача останавливается в `waiting_review` / `awaiting_approval`. Нода пока отсутствует в `nodes.json`, публичных hosts и DNS-выборе Auto. Для неё создан отдельный временный профиль Remnawave и отдельный internal squad: обычные клиенты в него не включаются. В этот squad временно добавляется только существующий `SERVICE_PROBE`. Подключение проверяется на настоящем входе 443 через исходный домашний Raspberry; отдельно RAW и XHTTP, если он включён. Используются прежние тестовые 2 КБ и 1 МиБ, SHA256 и IP выхода. Перед проверкой подтверждаются часы, контрольный HTTPS и внешний адрес домашней сети. Часовой манифест мониторинга не меняется; общий lock исключает одновременный запуск с часовой проверкой. Занятый или недоступный Raspberry означает «проверка не завершена», а не «нода заблокирована».

В карточке установки доступны:

- «Проверить ещё раз» — новая проверка с Raspberry без повторной установки Ubuntu.
- «Получить ключ для телефона» — отдельный VLESS TCP/RAW ключ с доменом кандидата, сроком 2 часа и общей квотой 1 ГБ. Он работает только на изолированной ноде; служебный ключ мониторинга пользователю не выдаётся. Повторное получение до истечения сохраняет тот же ключ; после истечения можно получить новый. Ключ показывается только в защищённом ответе по кнопке, отсутствует в обычном статусе, истории и логах. На сервере журнал с UUID зашифрован. Это временный профиль для проверки, а не вторая пользовательская подписка.
- «Всё работает — запустить» — явное подтверждение актуального результата. Администратор вправе подтвердить и после неудачной РФ-проверки, если его телефон работает у другого провайдера. Перед публикацией временный ключ отзывается, нода переводится на основной стандартный профиль, повторно проверяются HTTPS и UDP-DNS из Литвы. Только затем создаётся публичный host и страна появляется в существующих подписках, с выбранными при установке флагами Auto/RU. Пользователям требуется обычное обновление подписки.
- «Отменить добавление» — отзыв тестового пользователя, удаление принадлежащих кандидату VPN/HTTPS-контейнеров, приватного RU-peer, служебного канала, DNS и записи панели. На удалённом сервере обязательно проверяется `identity.json` с ID установки. Другие ноды и домашний 3x-ui не затрагиваются. Сервер у хостинга, обновления пакетов и уже проверенный ключевой SSH-вход сохраняются. Если SSH недоступен, отмена остаётся с ошибкой и может быть повторена; успех не имитируется. История и резервирование IP сохраняются, повторное добавление этого отменённого IP требует служебного сброса резерва.

Подтверждение привязано к версии результата; устаревшая вкладка не может опубликовать другой результат. Если основной конфиг изменился, нужно повторить проверку: обновляется только изолированный профиль кандидата, старый тестовый ключ отзывается. Перезапуск менеджера сохраняет ожидание решения. Идемпотентные действия не запускают две публикации/отмены. Ошибка РФ-проверки не публикует и не удаляет кандидата автоматически. Эта процедура применяется только к новым зарубежным нодам; замена российского выхода использует прежний отдельный установщик.

Код: `node_manager/onboarding.py`, `onboarding_probe_remote.py`, `onboarding_cancel_remote.py`, `NodeInstallation.jsx`. Зашифрованный журнал `install_candidates` и идемпотентные решения `install_actions` находятся в `manager.sqlite3`. Файл `pending-nodes.json` содержит только UUID и IP ожидающих нод: DNS-сверка сохраняет их домены для теста, но он не служит входом балансировщика. После публикации/отмены временная запись удаляется. Пользователи `NODE_TEST` исключены из персональных назначений Auto; бизнес-аккаунт или платёж не создаётся.

Ограниченный токен установки не получает новых прав на пользователей/группы. Операции с изолированным профилем, squad и временным пользователем выполняются существующей root-обёрткой `ConfigPanel`, используемой редактором VPN. Сайт передаёт только ID задачи и четыре допустимых действия, а не произвольный метод API или ID пользователя. Учётные данные панели остаются на главном сервере.

Служебное управление существующих зарубежных нод использует `wg-control`, сеть 10.77.0.0/16. API нод не открывается для произвольного интернета. Обновление ключевого SSH-входа проверяется до запрета парольного входа. Исходные введённые SSH-данные нормальных нод хранятся зашифрованно в root-хранилище; их просмотр требует отдельного права.

Задача имеет ID, фазу, историю и возможность повтора. Повтор не должен создавать вторую ноду или другой профиль. Не публиковать незавершённую или не прошедшую проверку локацию. Тестировать отказ до публикации и восстановление после перезапуска очереди.

Если включён RU, нода получает отдельный прямой WireGuard-peer российского выхода. При временном отказе настройки служба обслуживания повторяет её, а native Xray сохраняет обычный выход как резерв.

## Настройки, порядок и удаление нод

Карточка ноды показывает CPU, RAM и диск процентами и шкалами, абсолютные объёмы, дату измерения, расход/лимит трафика, сброс, стоимость и заметку. CPU рассчитывается по разности `/proc/stat`, RAM — через `MemAvailable`; загрузка CPU за мгновение не равна средней за весь день.

«Настроить» меняет квоту, скорость, сброс, обслуживание, Auto, RU и заметку. Изменение только заметки не должно перезапускать VPN. «Доступ» — отдельное раскрытие сохранённых SSH-данных после проверки прав. Секреты не хранить в localStorage и не отдавать обычным GET нод.

В «Порядке ключей» работают стрелки на телефоне и перетаскивание на компьютере. Порядок общий для подписок. В «Маршрутах» выбирается конечная локация и вход через другую ноду; петли, подключение через себя и чрезмерно длинные цепочки запрещены. При ошибке возвращается прежняя конфигурация.

На схеме обычный интернет и RU представлены отдельными ветками для выбранной локации. RU-ветка идёт через служебный российский выход только при включённой галочке. Схема показывает настройку; при отказе российского канала работает описанный ниже резервный DIRECT.

Удаление требует явного подтверждения имени и IP, сначала исключает ноду из подписок/Auto, затем останавливает принадлежащий сервису контейнер и отзывает служебные связи. Операционная система и резервные копии остаются. Нельзя удалить последний рабочий сервер, чужой неуправляемый сервер или ноду с зависимыми маршрутами. Перед удалением Турции/Литвы нужно корректно разобрать их цепочку. Серая кнопка сопровождается причиной, а не означает сломанный интерфейс.

## Напоминания об оплате серверов

В «Ноды → Настроить» и при добавлении есть **«Напоминать об оплате»**, по умолчанию включено, включая прежние записи без этого поля. `Metadata.payment_reminders_enabled` хранится вместе со стоимостью в закрытом `site-admin.sqlite3.inventory.metadata`; чтение старой записи не переписывает данные. Запрос старого клиента без нового поля сохраняет уже выбранное отключение. Доступ к изменению — прежнее серверное право `nodes`, Telegram 2FA и CSRF. Отсутствующая/нулевая месячная стоимость не создаёт напоминаний независимо от флажка. Скрытие ноды или обслуживание не отменяет необходимость оплачивать VPS; полное удаление ноды, удаление стоимости либо выключение флажка отменяет её незавершённые уведомления.

Днём оплаты считается существующий `reset_day` (оплата и сброс трафика), начало даты — **00:00 МСК (UTC+3)**. Первое сообщение — за 24 часа, затем через **6 часов после подтверждённой отправки** каждого сообщения, пока владелец не нажмёт **«✅ Оплачено»**. Для 29–31-го в коротком месяце берётся последний день. В сообщении — название/IP, сумма/валюта, дата и кнопка. Подтверждение относится только к указанному месяцу и **не оплачивает хостинг автоматически**; следующий месяц снова напоминает. Старая кнопка не подтверждает новый период. Если новый расчётный период начался до подтверждения прошлого, остаётся одно актуальное напоминание на ноду вместо накапливающейся пачки старых счетов.

`node_manager/billing.py` создаёт ограниченное долговечное состояние в `manager.sqlite3`: `billing_meta`, `node_bills`, `billing_outbox`. Планирование выполняется при опросе бота раз в 30 секунд; поэтому напоминания продолжаются без открытого сайта или чата Codex. Первый запуск не создаёт задним числом счета за уже прошедшие даты. Отправки с lease 5 минут и транзакционным claim; после успешной доставки бот подтверждает message_id, только затем назначаются следующие 6 часов. Ошибки доставки повторяются после lease. Редкий сбой между доставкой Telegram и записью подтверждения может привести к повторному сообщению: Telegram sendMessage не предоставляет сквозной ключ идемпотентности. Рестарт не стирает подтверждение оплаты, график или очередь. История счетов ограничена 400 днями, завершённые уведомления/их кнопки — 90 днями. Логи содержат код/класс ошибки, ID счёта/ноды, без паролей и приватных ключей.

Бот `staging/bot/node_billing.py` использует существующий узкий Unix-сокет node-review: `/billing/claim`, `/billing/ack`, `/billing/callback`. Мост разрешает только эти фиксированные операции; root-токен и SSH не передаются в бот. Callback `kb:<24 случайных символа>` привязан к одному счёту; отдельно проверяется Telegram ID владельца из `ru-monitor.json.owner_id`, независимо от активности мониторинга РФ. Чужой Telegram-пользователь не может подтвердить оплату даже с копией кнопки. Изменённая дата/отключённый или удалённый сервер делает прежнюю кнопку неактуальной. Успешное подтверждение заменяет текст исходного сообщения и убирает кнопку. При недоступности Telegram напоминания остаются в очереди. Проверки сценария выполняются на временном хранилище и поддельном Telegram, без ложных реальных сообщений и изменения платёжных дат рабочих нод.

## Российский выход и правила доменов

Исходный получатель — домашний Raspberry Pi 5, Debian ARM64, новая служебная Remnawave-нода рядом со старым 3x-ui. В клиентскую подписку РФ-профиль не добавляется. У каждого зарубежного сервера галочка определяет отправку российских сайтов через него.

Перенесён точный список доменов старой маршрутизации:

```text
domain:ru
domain:xn--p1ai
domain:vk.com
domain:boosty.to
domain:donationalerts.com
domain:tamtam.chat
domain:yandex.cloud
domain:yandex.com
domain:yandex.net
domain:yandexcloud.net
domain:yandexmetrica.com
```

Старые блокировки IP-проверок и MAX не являются этим списком и автоматически не копировались. Изменение списка — существенное изменение: обновить backend-политику, проверки и этот документ.

Главный сервер управляет получателем по отдельному `wg-ru-control` с адресом ядра `10.79.0.1`; исходный Raspberry имеет `10.79.0.2`. Пользовательский RU-трафик идёт напрямую между зарубежными нодами и РФ-выходом, по `wg-ru`, сеть исходного поколения `10.78.0.0/24`. Внутри WireGuard используется приватный VLESS-порт 15443. Порт управления 2222 доступен только из закрытой сети ядра, а 15443 — только через RU-сеть. Внешний REALITY пользователя сохраняется.

Дания, Литва и Турция имеют прямые частные связи с Raspberry. Для Германии прямой канал не заработал; владелец отказался от промежуточной пересылки через Литву. Поэтому Германия использует обычный выход для RU. Не включать скрытый промежуточный маршрут вместо её выключенной галочки.

Внутренний outbound `KINGLINE_RU` находится в общем профиле; native observatory проверяет его примерно раз в 30 секунд, балансировщик имеет DIRECT как резерв. Выключенная RU-галочка отзывает peer и задаёт локальный недоступный маршрут для частного получателя, чтобы нода использовала обычный выход. Это позволяет сохранять общий стандарт входящих настроек. При отказе RU возможна задержка обнаружения и переподключение уже открытых соединений.

Домашний DNS выдавал синтетические адреса 198.18/15. Новый RU-контейнер использует отдельный DNS через HTTPS на 1.1.1.1/1.0.0.1; роутер и старый VPN не менялись. Не возвращать localhost DNS без проверки, иначе отдельные сайты могут перестать открываться.

## Автоматическая замена РФ-сервера

«Ноды → Российский выход → Заменить РФ-сервер» принимает публичный IP российского сервера, SSH-порт, название и пароль root/ключ. Сервер должен быть доступен с главного сервера. Приватный домашний IP за NAT сам по себе недостаточен для первичного входа из дата-центра; нужен доступный SSH или предварительно настроенный канал.

Получатель поддерживает Ubuntu 22.04/24.04/26.04 и Debian 12/13, amd64 или arm64. На неизвестном сервере с другим VPN/контейнерами автоматическая установка останавливается. Существующий принадлежащий сервису RU-получатель можно готовить рядом, не удаляя его старые службы.

Последовательность:

1. Проверить SSH, систему и отсутствие конфликтов; зафиксировать отпечаток хоста.
2. Установить и проверить служебный SSH-ключ, затем убрать исходный пароль из журнала задачи и запретить парольный root-вход.
3. Установить зависимости и выделить новое поколение частных сетей/контейнера, отдельно от работающего получателя.
4. Подключить управление к ядру и подготовить прямые WireGuard-peer всех нод с включённым RU.
5. Запустить контейнер Remnawave, привязать к отдельному внутреннему RU-профилю и дождаться готовности ядра.
6. Проверить HTTPS и UDP-DNS через каждый подготовленный частный канал, не переключая клиентские маршруты.
7. Сохранить зашифрованный план восстановления, проверить конфигурации Xray, переключить внутренний RU-target и проверить реальные публичные входы.
8. Зафиксировать новый получатель только после успешных проверок. Отключить прежнюю служебную RU-ноду и её частные peer; прежний 3x-ui не затрагивать.

Во время подготовки старый выход продолжает работать. Переключение внутренних конфигураций может кратко переподключить VPN; профиль, UUID и ссылка пользователя не заменяются. Если проверка не проходит, возвращаются исходные профили. Если автоматическое восстановление не завершилось, задача показывает отдельную ошибку и требует проверки технических логов, а не ложного «Готово».

Очередь `ru_jobs` — в SQLite менеджера. Пароль и контекст с резервными конфигурациями шифруются. В публичном API только этапы, время, IP задачи и безопасный прогресс по нодам. Незавершённая задача возобновляется после перезапуска; повтор использует тот же контекст. Одновременная замена RU и изменение сетевых настроек блокируются.

Для поколения G используются `10.78.G.0/24` и адрес управления `10.79.G.2`; нулевое поколение сохраняет исходные адреса. Имена контейнеров и интерфейсов различаются по поколению. Текущий простой адресный план ограничен 254 поколениями и одной /24 для peer; перед масштабированием до сотен серверов его нужно расширить и проверить уникальность адресов.

Файлы/модули: `ru_installer.py`, `ru_egress.py`, `ru_receiver_remote.py`, `ru_mesh_remote.py`, `ru_policy.py`. Состояние `/opt/kingline-control/ru-egress.json` содержит секрет внутреннего доступа — его нельзя отдавать браузеру или копировать на Mac. Периодическое обслуживание — `kingline-ru-egress.timer`. Ресурсы публикуются отдельным безопасным `ru-resources.json`.

## Проверки входов из домашней сети РФ

Проверяющий модуль установлен на исходном домашнем Raspberry. Он использует уже разрешённого технического пользователя `SERVICE_PROBE`, а не профиль владельца. В часовых проверках выбираются только прямые входы: ноды без промежуточного `via`. Турция, пока её вход идёт через Литву, отдельно напрямую не проверяется. После смены маршрутов и добавления нод список обновляется автоматически. Скрытые прямые входы продолжают проверяться для обнаружения восстановления.

Программа `/opt/kingline-ru-monitor/worker.py` запускается на Raspberry через `kingline-ru-monitor.timer` каждый час, с небольшим сдвигом до минуты. Проверку можно запросить кнопкой в Telegram или «Ноды → Проверка из России». Начальная проверка запускается сразу. Отдельный пользователь Linux `kingline-probe`, лимиты памяти/CPU, read-only системные пути и отдельный Xray ограничивают влияние на прежний 3x-ui и RU-ноду. Бинарник берётся из уже установленного официального контейнера Remnawave; после копирования монитор не зависит от его дальнейшего запуска.

Проверка устанавливает TCP к реальному входу, запускает VLESS RAW/REALITY/Vision с актуальными SNI/ключом/отпечатком, скачивает 2 КБ, затем 1 МиБ известного несжимаемого файла. Проверяются размер, SHA256 и фактический IP выхода. Большая передача идёт примерно 32 секунды, что позволяет заметить остановку после первых пакетов. При неудаче выполняются до трёх попыток с паузами. Пропадание после пяти–десяти минут или только в определённом приложении такая короткая проверка не исключает.

Контрольный ресурс — `/api/connectivity/probe.bin` на новом главном сервере: фиксированные данные без БД, без авторизации и без пользовательского содержимого. Поддержаны полный ответ и единственный диапазон 0–2047; неизвестные диапазоны отвергаются. Обычная успешная часовая проверка расходует около 0,75 ГБ в месяц на входную ноду, плюс небольшие служебные запросы и повторы.

Прямой контрольный запрос фиксирует внешний IP Raspberry; он сравнивается с фактическим endpoint домашнего WireGuard-peer на главном сервере. Это помогает заметить, что сам проверяющий путь оказался за другим VPN. Проверка часов и контрольного интернета отделяет сбой Raspberry от отказов нод. Проверка охватывает именно эту домашнюю сеть: результат не доказывает доступность у Билайна, МТС или всех других операторов РФ.

Главный сервер раз в минуту синхронизирует закрытый манифест и собирает отчёт по существующему SSH/WireGuard. Новых публичных административных портов нет. `/opt/kingline-control/ru-monitor.json` содержит адрес и отпечаток именно проверяющего Raspberry, независимо от текущего RU-выхода. Замена российского VPN-выхода не переносит домашний измеритель в дата-центр; его прежний канал управления должен оставаться доступным. При потере связи более десяти минут отправляется отдельное предупреждение о проверяющем, без объявления всех нод заблокированными.

## Диагностика фильтрации и уведомления

Основа алгоритма — сравнение измерений из РФ и свежих проверок из Литвы, повторяемость ошибки и работоспособность других входов. При повторном сбое главный сервер дополнительно проверяет тот же файл через тот же профиль из Литвы: ошибка контрольного ресурса или пути от ноды не должна выдаваться за российскую фильтрацию. Две неудачи из трёх подтверждают техническую проблему. Один сбой с двумя успешными повторами сам по себе не создаёт тревогу; повторение нестабильности в соседних часовых проверках уже требует внимания.

Различаются: невозможность TCP-подключения, отказ REALITY/TLS, остановка передачи на похожем объёме, непредсказуемые обрывы, неверный IP выхода и отказ самой ноды. Если из Литвы тоже есть ошибка, нельзя считать это доказательством региональной фильтрации. Устаревший отчёт или отчёт прежней конфигурации не применяется. Ошибки часов, контрольной сети или запуска проверяющего ядра не превращаются в массовое скрытие нод.

Исследовательская основа: [OONI о TLS-вмешательстве в РФ](https://ooni.org/post/2024-russia-blocked-ooni-explorer) описывает таймауты и RST после ClientHello; [наблюдения Cloudflare за июнь 2025](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet/) описывают остановку загрузок после первых примерно 16 КБ. Эти признаки не универсальны и не устанавливают виновника. Наш диапазон остановки шире; в уведомлениях используется формулировка «возможная фильтрация», а не «доказанная блокировка РКН».

При подтверждённой проблеме владелец получает сообщение `ВАЖНО` в новом боте `@stopRKNbot`. Кнопки: «Проверить», «Оставить», «Скрыть из подписок», «Через другую ноду». «Оставить» не меняет сервис; при сохраняющейся проблеме напоминание возможно через сутки. Одинаковая часовая ошибка не порождает новое сообщение каждый час. После восстановления приходит отдельное уведомление; скрытый профиль автоматически не возвращается.

Бот имеет только отдельный Unix-сокет `/run/kingline-node-review/bot.sock`, смонтированный как `/run/node-review/bot.sock`. В нём закрытые действия: получить уведомления проверки РФ или оплаты серверов, подтвердить отправку, передать нажатие соответствующей непрозрачной кнопки. Ключ root-менеджера, SSH и общий административный сокет в бот не передаются. Решения принимаются только от Telegram ID владельца, с привязанным к задаче случайным токеном. Повторное нажатие изменения идемпотентно; устаревшая кнопка не меняет новую конфигурацию. «Проверить» можно снова использовать после окончания прежней проверки. Telegram-отправка выполняется из Литвы, поэтому блокировка Telegram в домашней сети не мешает доставке.

## Скрытие, рассмотрение и новый вход

В «Нодах» появился блок «Проверка из России»: результаты, диагностика попыток, очередь решений и скрытые локации. Право `nodes` разрешает просмотр, проверку, скрытие/возврат; назначение промежуточного входа дополнительно требует `vpn_config`. Сайт сохраняет Telegram 2FA и CSRF. Telegram-кнопки доступны только владельцу; это самостоятельный канал управления, подтверждённый Telegram-идентичностью и токеном действия.

Скрытие — флаг `hidden` и отключение публикации Remnawave host, без удаления ноды, контейнера или пользователей. Если вход скрыт, зависимые от него профили тоже скрываются (`effective_hidden`, `hidden_by`). «Умный выбор» исключает скрытый вход при ближайшем обновлении контроллера; прежние веса и ручные настройки сохраняются. Возврат восстанавливает предыдущее состояние host, в том числе не включает ранее вручную отключённый host. Для изменений есть зашифрованный журнал и компенсация при сбое API.

Изменение списка становится видимым пользователю после обновления подписки. Уже сохранённый VLESS-ключ и существующее соединение скрытие не отзывают. Для полного удаления используется прежняя отдельная функция с проверками и подтверждением IP/имени. Не заменять скрытие удалением ради мониторинга.

«Через другую ноду» предлагает прямые, не скрытые входы со свежей успешной проверкой из РФ и без циклов. Профиль временно скрывается, применяется существующая транзакция маршрутов, затем Raspberry проверяет фактический новый вход и порт. Только после успешного результата профиль публикуется. При отказе он остаётся скрытым. Если владелец во время ожидания выбирает оставить профиль скрытым, автоматическое возвращение отменяется. Повторное назначение входа или ручной возврат блокируются до окончания текущей проверки; для отмены автоматического возвращения можно повторно скрыть профиль.

Локация за промежуточным входом становится ручной: DNS-«Умный выбор» использует только прямые входы. После перевода на другой вход необходимо обновить подписку в приложении. Главный сервер по-прежнему не передаёт пользовательский VPN-трафик.

Состояние мониторинга, решения, кнопки и очередь доставки — в `manager.sqlite3`. Измерения хранятся 30 дней, завершённые уведомления и запросы — 7 дней, завершённые рассмотрения — 90 дней. Сырые пакеты, полезная нагрузка и вывод Xray с ключами не сохраняются; в отчёте только ограниченные числовые показатели и фиксированные коды. Резервная копия менеджера и `ru-monitor.json` остаётся на сервере.

## Данные, телеметрия и приватность

Пользователи, балансы, оплаты, привязки и поддержка находятся в основной бизнес-SQLite. Конкретное имя файла определяется `DB_PATH`/`KINGLINE_DB_PATH` в закрытом окружении. Remnawave хранит собственные данные в PostgreSQL; это другая база, её нельзя заменить копией бизнес-SQLite.

Техническая телеметрия вынесена в `/opt/kingline-staging/logs/telemetry.db`, отдельно от бизнес-базы. `compact_metrics.py` использует словари измерений, временные bucket-агрегаты и суточные сводки доменов вместо миллионов одинаковых строк. Окно подробных bucket — 7 дней, сводок — 90 дней. Основной предел SQLite — 128 MiB, WAL ограничивается отдельно. Это не размер основной бизнес-базы и не бесконечное хранение истории посещений.

Исторический архив прежних технических таблиц лежит отдельно на сервере. Он не должен подключаться на каждый запрос кабинета. Сырые старые журналы не переносить назад в рабочую базу и не выдавать в обычном списке пользователей.

Журналы диагностики не содержат тела переписки, содержимого VPN-трафика и реальных секретных URL. Доступ к пользовательской активности определяется административными правами. Отсутствующие сведения об операторе не выдумываются: GeoIP/ASN получают в фоне, пустые результаты повторяют раньше положительных.

Сеть «домашняя/мобильная» — вывод из оператора, а не измерение радиотехнологии телефона. Публичный IP и регистрационный HWID имеют разный смысл. В онлайне показываются фактические коды локаций и число недавних IP отдельно от зарегистрированных устройств. По серверным данным нельзя достоверно назвать ручную локацию «Авто», если клиент не передаёт способ выбора.

В верхнем блоке «Онлайн» общий счётчик означает пользователей с активностью за последние 3 минуты. Пользователи показаны компактными кнопками: имя/логин, короткие коды локаций и небольшой бейдж зарегистрированных устройств `N/лимит`. Полное имя, недавние IP по локациям и пояснение счётчика доступны в подсказке; нажатие открывает пользователя. Бейдж устройств не является числом одновременных подключений. Длинные имена сокращаются визуально; строка пользователя не переносится внутри кнопки. В списке остаются прежние 18 пользователей и индикатор количества остальных. Изменение оформления не меняет сбор онлайна или ограничения устройств.

## Технические логи и наблюдаемость

Раздел показывает текущее состояние служб отдельно от исторических ошибок, график ошибок за сутки, фильтры по уровню/службе/коду, сведения события и выгрузку. Ошибка вчера не означает, что служба сейчас неисправна. Успешный HTTP `/health` не заменяет реальную проверку туннеля.

События имеют время UTC, службу, уровень, тип, request_id, job_id/фазу, длительность и безопасные кадры стека. Пароли, cookies, токены, email, private key и секретные URL маскируются. Не логировать произвольный JSON внешнего API при ошибке.

Основные источники — журналы сайта/бота, `node-manager`, `site-admin`, операций и небольшая диагностика RU-обслуживания. Обычные источники ротируются по 2 MiB × 4; журнал RU — 256 KiB × 3. Чтение ограничено размером и числом событий, кэшируется, не сканирует старый многомиллионный архив.

Показатели CPU/RAM/диска не копят бессрочную историю: публикуется ограниченный свежий снимок. Устаревшие данные помечаются, а не выдаются за текущие. RU-состояние дополнительно учитывает подключение Remnawave и uptime ядра.

Служебный `SERVICE_PROBE` создан с разрешения владельца для автоматических проверок. Он исключён из пользовательских показателей. Нельзя снова использовать профиль владельца для постоянного мониторинга: это искажает онлайн и локации.

## Основные API

Публичные сессии и административные проверки обслуживаются HTTP-сайтом. Root API менеджера слушает только localhost и требует токен; браузер его не получает. Root-мост дополнительно ограничен Unix-сокетом.

| Интерфейс | Назначение |
|---|---|
| `/api/auth/...` | Авторизация и аккаунт |
| `/sub/<токен>` на новом сайте | Совместимая выдача подписки |
| `/api/admin/infrastructure/nodes` | Список нод, показатели и очереди |
| `/api/admin/infrastructure/add`, `preflight`, `update`, `remove`, `retry` | Управление нодой |
| `/api/admin/infrastructure/node-reviews` | Проверки из РФ и рассмотрение |
| `/api/admin/infrastructure/review-check` | Запрос повторной проверки |
| `/api/admin/infrastructure/review-action` | Решение по инциденту |
| `/api/admin/infrastructure/installation-action` | Проверить кандидата, выдать временный ключ, подтвердить или отменить установку (`nodes`, 2FA, CSRF) |
| `/api/admin/infrastructure/node-visibility` | Обратимое скрытие/возврат |
| `/api/admin/infrastructure/credentials` | Явное раскрытие SSH-данных, отдельное право |
| `/api/admin/infrastructure/node-network`, `node-connection`, `node-routes`, `node-order` | Маршруты, SNI/target, порядок |
| `/api/admin/infrastructure/ru-egress` | РФ-выход и история задач |
| `/api/admin/infrastructure/ru-replace`, `ru-retry`, `ru-job` | Автоматическая замена и прогресс |
| `/api/admin/infrastructure/logs` | Диагностика, отдельное право |
| `/api/admin/documentation`, `/api/admin/documentation/export` | Документация, отдельное право |
| `/api/admin/messages/announcement` | Текст объявления в VPN-приложении, GET/POST, право `broadcast`, 2FA и CSRF для POST |
| `127.0.0.1:8090/v1/...` | Закрытые операции менеджера |

Ошибки API возвращают стабильные коды и идентификатор запроса, не входные пароли и не trace с секретами. Мутации имеют ограниченный размер тела. Повторы установки используют идемпотентный ID. Не обходить серверные права прямым обращением frontend к root API.

## Эксплуатация и поиск неполадок

Начать с технических логов: текущие службы, состояние коллектора, RU-выхода, DNS и очередей. Затем ID проблемного запроса/задачи, время UTC и безопасный код. Передать ИИ выгрузку документации и отфильтрованные диагностические события; не отправлять `.env`, токен подписки или privateKey.

Типовые случаи:

| Симптом | Что проверить |
|---|---|
| Подписка пуста | Срок/блокировку, `remna_links`, native ответ и HWID-заголовки, совместимость приложения |
| REALITY возвращает обычный сертификат | Адрес/порт/SNI/publicKey/shortId, актуальность подписки, версию ядра и часы; затем реальную сеть пользователя |
| Только российские сайты не открываются | Галочку ноды, RU-канал, observatory, DoH получателя, доступность конкретного сайта |
| Часть сайтов видит иной IP | Ручной выбор, цепочку, разделение RU/обычного трафика, failover и клиентский DNS-кэш |
| Оплата есть, доступа нет | Сохранённую операцию и повторы; не выполнять новое списание |
| Установка долго идёт | Фазу packages/pull/ожидание Remnawave; очередь выполняется в фоне |
| Серые кнопки удаления | Причину: зависимые маршруты, последняя нода, неуправляемый сервер |
| Нет ресурсов | Свежесть снимка и сборщик, а не немедленно перезапускать Xray |
| Не определён оператор | Фоновый GeoIP/ASN, TTL пустого результата и доступность внешнего источника |
| Ошибки Reverso | Отличить доступность сайта от API приложения; автоматический 403 сам по себе не доказывает поломку VPN |

Никакой конфиг не гарантирует обход всех операторских фильтров. Проверка реального пользователя и проверка из дата-центра — разные доказательства. При «на телефоне работает, на ПК нет» не менять сразу общую рабочую маскировку всех нод.

## Проверки перед существенным выпуском

Проверять затронутые серверные сценарии: права/2FA/CSRF, отсутствие секретов, идемпотентность, восстановление после сбоя и отказ до публикации. Для доменов — отказ до публикации при сбое DNS, точное удаление записей, сохранение имён при смене входа, продление сертификата и обычный HTTPS без VPN-ключа. Для маршрутов — HTTPS и UDP-DNS; для RU — частный канал и публичный вход с подтверждением ожидаемого выхода. Не удалять рабочую ноду для теста.

Для UI обязательны lint/build и проверка актуального интерфейса с безопасными данными. Узкие экраны — минимум 390 px, для затронутой поддержки/таблиц также 320 px. Схема может прокручиваться внутри собственного контейнера; страница целиком не должна расползаться. Не заявлять проверенным клик, который браузер не выполнил.

В тестах внешние оплаты, Telegram-отправки и установка нового сервера подменяются безопасными двойниками, если фактический сервер не предоставлен. Различать это от реальной установки. Проверка нового RU-установщика на двойниках не означает, что неизвестный будущий VPS уже развернут.

Базовые команды запускаются из корня проекта:

```sh
private/manager-venv/bin/python -m pytest -q node_manager/tests test_smart_dns.py test_sticky_dns.py
```

Frontend: `pnpm --dir staging/site lint` и `pnpm --dir staging/site build` в настроенном Node-окружении. Проверки сайта/бота выполняются в собранном Docker-образе на временной SQLite, не на пользовательской бизнес-базе.

## Развёртывание и резервные копии

До изменения сохранить серверную копию исходников/конфигурации и предыдущий Docker-образ. Бизнес-базу SQLite копировать через backup API, PostgreSQL — штатным дампом. Копии включают состояние менеджера, ключ шифрования, служебные SSH-данные, состояние RU/DNS-закрепления и WireGuard-конфигурации ядра. Без ключа шифрования зашифрованные данные не восстановить. При восстановлении главного сервера на другом публичном IP необходимо также обновить endpoint и ограничения доступа на удалённых нодах; одного копирования БД недостаточно.

Действующая политика — резервные копии только на серверах. Автоматическая ежедневная копия проверяет SQLite integrity и структуру дампа панели; хранит ограниченное число ежедневных поколений. Изменение сроков хранения и вынос копий с сервера — отдельное решение владельца.

Новый сайт/бот запускаются из `/opt/kingline-staging` через Docker Compose. Root-код менеджера развёрнут отдельно; системные службы и Unix-сокет не являются частью образа сайта. Сначала обновить совместимый backend, затем frontend/образ, выполнить проверки и проверить `/api/health`, состояние контейнеров и настоящий VPN.

Не пересоздавать каталог уже смонтированного Unix-сокета при рестарте. Не менять рабочий бот на тестовый токен или наоборот случайной подменой `.env`. Не сохранять stdout команд, которые могут вывести API-профиль или privateKey, в публичном отчёте.

## Восстановление и передача другому ИИ

Для сбоя сайта откатить образ/исходники и проверить сессии, бизнес-базу, worker и мост. Не перезапускать все VPN-ноды из-за ошибки CSS. Для сбоя одной локации сначала исключить её из Auto, сохранив остальные и причину отказа.

Для RU-замены использовать зашифрованный журнал `ru_jobs`: исходный получатель, сохранённые профили и факт фиксации нового. Нельзя слепо записывать старые профили поверх более новых ручных изменений. При `ru_rollback_incomplete` проверить фактические привязки и конфигурации до нового запуска.

Для отмены исходного RU-внедрения сначала остановить таймер обслуживания, вернуть сохранённые customer config-profiles, выключить `ru-egress.json.enabled` и удалить только новые частные связи/контейнеры. Старый 3x-ui и исходный `wg-control` не трогать. Для отката собственной HTTPS-идентичности использовать серверный `before-identity-*` и `identity-release-path`: восстановить canonical config-profiles, адреса/SNI hosts, owner-profile, settings и node-network; затем пересобрать инвентарь и DNS. Не восстанавливать целиком manager.sqlite3 поверх новых решений администратора. При обычном откате к прежнему target HTTPS-контейнер можно оставить до завершения диагностики: он не переносит VPN-трафик. Для отката DNS-закрепления сначала вернуть native upstream выдачи подписок, затем останавливать адаптер и возвращать контроллер.

Другому ИИ передать этот файл с динамическим снимком, цель изменения, свежую безопасную выгрузку логов и ID задачи. Не передавать пароли и полный дамп окружения. Новый ИИ должен проверить живое состояние, а не считать старые отчёты истиной. После существенного изменения обновить этот документ, тесты и развёрнутую защищённую копию; это правило закреплено в `AGENTS.md` проекта.
