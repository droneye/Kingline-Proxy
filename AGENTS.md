# Правила проекта Kingline

Основная актуальная документация — `staging/docs/service.md`. Она публикуется в
админке в разделе «Документация». Перед существенными изменениями прочитайте её.
После изменения архитектуры, API, БД, прав доступа, установки, маршрутов,
выдачи подписок, оплаты или эксплуатации обновите этот файл и проверьте его
защищённую выдачу. Старые отчёты в корне и staging — история, а не текущая спецификация.

Пользователь просит сохранять одну подписку для всех устройств: не вводите
отдельные ссылки/подписки для ПК в инструкциях.

Главный новый сервис — 198.51.100.10. Старый рабочий сервис 198.51.100.20
не переключать и не отключать без отдельного указания. На домашнем Raspberry
старый 3x-ui работает параллельно; автоматизация нового RU-выхода его не удаляет.
Германия по выбору владельца сейчас использует обычный выход для RU-трафика.

Базы пользователей/платежей, реальные VPN-ключи и их резервные копии хранить
только на серверах. Не загружать их на Mac. Не выводить целиком .env,
owner-profile.json, API-профили с privateKey, пароли, токены и ссылки подписок.
В документацию и диагностические выгрузки секреты не включать.

Используйте доступные модели/SQL/SSH-обёртки. Не удаляйте рабочие ноды для теста.
Новую RU-ноду готовьте параллельно, переключайте только после проверок,
сохраняйте зашифрованный журнал и возможность восстановления. Проверки
пользовательских туннелей используют разрешённую служебную SERVICE_PROBE-запись.
Не создавайте новые VPN-доступы или Telegram-рассылки ради проверки без основания.

Для административных разделов нужны серверная проверка отдельного права,
Telegram 2FA и CSRF для изменений. Одного скрытия кнопки недостаточно.
Новые права у обычных администраторов по умолчанию выключены.

Развёртывание нового сайта/бота касается изолированной площадки и тестового
бота, пока владелец не разрешил производственное переключение. Не заменяйте
имитацию оплаты реальным списанием и не запускайте копию рабочего Telegram-бота.

В отчёте различайте проверки на поддельных SSH/API, реальные проверки
существующих туннелей и фактическую установку нового сервера. Не объявляйте
клиентский или операторский сбой исправленным без соответствующей проверки.

Проверки из РФ — отчётные: не включайте автоматическое скрытие по их результатам.
Решение принимает владелец/уполномоченный администратор. Технический SERVICE_PROBE
не выдаётся пользователям. Не отправляйте ложные боевые тревоги ради теста:
отказы проверять на двойниках, а фактические уведомления — по реальному результату.
При замене RU-выхода домашний измеритель остаётся отдельной ролью. Telegram-боту
разрешён только узкий сокет node-review, без общего root-моста и SSH-ключей.
